# 💻 Coding Style & Architecture Guidelines

너는 코드의 결합도(Coupling)를 최소화하고, 단일 책임 원칙(SRP)을 철저히 지키는 코드를 작성해야 해. 코드를 제안할 때는 반드시 아래의 스타일 가이드를 엄수해 줘.
파일을 읽을 때 속도를 위해 방대한 엔진 파일들은 무시하고, 반드시 프로젝트 내의 코드만 참고해. 또한, 기존 시스템과의 결합도를 최소화하고, 컴포넌트/데이터에셋 패턴을 유지하는 방식으로 코드를 작성해야 해. 

## 1. 파일 제공 원칙 (필수)
- C++ 코드를 작성하거나 수정 사항을 제안할 때는 **반드시 헤더 파일(.h)과 소스 파일(.cpp)을 세트로 함께 제공**해야 해. 한쪽 파일의 변경 사항만 누락 없이 완전한 쌍으로 구성해 줘.
- 변경 사항은 알아보기 편하게 주석으로 표시해줘.
- 그리고 앞으로는 코드, 답변들을 주기 전에 해당 코드의 효과, 의도를 먼저 알려줘.
- 코드나 답변을 다 준 이후에는 현재 진행 상황을 체크해서 다음에 할 일들의 추천 목록 또는 우선순위를 정리해서 알려줘.


## 2. 아키텍처 및 설계 원칙
- **컴포넌트 분리:** 핵심 로직(스탯, 이동, 스킬 관리 등)은 `AActor`에 직접 구현하지 않고, 반드시 `UActorComponent`로 분리하여 조립(Composition)하는 방식을 사용해.
- **데이터 주도 설계:** 기획자가 수정해야 하는 스킬 수치, 카드 정보, 아이템 속성 등은 하드코딩하지 않고 `UPrimaryDataAsset`을 상속받는 데이터 클래스로 분리해.
- **컨트롤러 보호:** `PlayerController`나 `GameMode`에는 순수하게 입력 전달과 게임 흐름 제어 로직만 남겨둬. 구체적인 실행 로직은 외부 매니저(예: `CheatManager`)나 각 컴포넌트로 위임해.
- **에러 예방:** 함수 호출 시 `nullptr` 체크, 유효성 검사(`IsValid()`)를 철저히 수행하고, 예외 상황 발생 시 로그(`UE_LOG`)를 남겨 디버깅에 도움을 주도록 해. 로그 텍스트 앞에 [클래스명] 형식으로 표기하여 로그 발생 위치를 명확히 해. 타이머를 사용할 때에도 발생할 수 있는 예외 상황을 고려하여 안전하게 처리하도록 해.

## 3. C++ 코딩 컨벤션
- **헤더 최적화:** 헤더 파일에서는 불필요한 `#include`를 피하고, 전방 선언(Forward Declaration, `class ClassName;`)을 적극적으로 활용해.
- **Early Return:** 함수 내부의 들여쓰기(Depth)가 깊어지는 것을 방지하기 위해, 예외 처리나 유효성 검사(`IsValid()`, `nullptr` 체크) 시 'Early Return' 패턴을 최우선으로 사용해.
- **이벤트 기반 통신:** UI 갱신이나 시스템 간의 통신은 직접 참조를 피하고, `DECLARE_DYNAMIC_MULTICAST_DELEGATE`를 활용한 이벤트 디스패처 구조로 작성해.

## 4. 에디터 친화적 코딩
- 에디터 전용 로직이나 툴링 코드를 작성할 때는 반드시 `#if WITH_EDITOR` 매크로로 감싸서 패키징 빌드에 영향을 주지 않도록 해.
- 변수에는 명확한 `Category`를 지정하고, 에디터에서 조작해야 하는 변수는 `EditAnywhere` 또는 `EditDefaultsOnly`를, 읽기 전용 상태 변수는 `VisibleAnywhere`를 정확히 구분해서 사용해.

## 5. 언어 설정
- 코드의 주석과 코드 구현에 대한 모든 설명은 명확한 한국어로 작성해 줘.
